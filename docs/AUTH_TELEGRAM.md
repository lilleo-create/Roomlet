# Telegram и сессии Roomlet

## Состояние Phase 02.3

Каталог работает без входа. На экране аккаунта Telegram показан как основной будущий способ входа с явной подписью о доступности. Сейчас пользователь может войти по почте. Для Telegram реализована [серверная проверка initData](../src/lib/telegram/init-data.server.ts) с четырьмя [регрессионными тестами](../tests/telegram.test.ts). Она возвращает проверенный ID и доступные данные профиля. В этой фазе ещё не развёрнуты автоматический обмен доказательства запуска, OIDC-посредник и выдача сессии через Telegram. Установка секрета сама по себе вход не активирует.

## Одна идентичность для Mini App и браузера

Постоянный идентификатор Roomlet — существующий UUID `auth.users.id`. С ним связаны `profiles.id`, заказы и права. После привязки Telegram у пользователя с почтой сохраняется тот же UUID.

| Этап | Доказательство и ключ |
| --- | --- |
| Telegram Mini App | Подтверждённый HMAC запуска и числовой `user.id` |
| Telegram Login в браузере | Проверенный ID-токен официального Telegram OIDC. `iss + sub` идентифицируют пользователя у провайдера. Scope `profile` даёт отдельный числовой `id` для сопоставления с Mini App. |
| Оба канала → Supabase | Один OIDC-провайдер Roomlet с постоянным issuer и субъектом `tg:<десятичный Telegram id>`. У тестового и рабочего провайдеров разные issuer и ключи. Связь субъекта с единственным UUID хранит Supabase в `auth.identities`. |

В проекте интеграции серверный OIDC-посредник принимает два типа доказательств для одного зарегистрированного бота. На веб-сайте он делегирует вход официальному Telegram Login, в Mini App проверяет подпись запуска. Для Supabase он выглядит одинаково в обоих случаях. Прямой провайдер Telegram OIDC сам по себе не принимает `initData`. Два независимых провайдера без общей идентичности могут создать разные UUID.

Числа `sub` и `id` в опубликованном примере Telegram различаются. При отсутствии проверенного числового `id` обмен прекращается до создания аккаунта. Имя, username и фотография служат для отображения. При первом входе подтверждённое имя можно использовать для пустого профиля, при повторном входе выбранное пользователем имя сохраняется. [Поля Telegram Login](https://core.telegram.org/bots/telegram-login#available-scopes)

## Автоматический вход в Mini App после подключения

1. При запуске приложение проверяет существующую сессию Supabase. Если сессии нет и `Telegram.WebApp.initData` заполнена, клиент передаёт строку серверу в теле HTTPS POST с того же origin. В обычном браузере посетитель остаётся гостем. `initDataUnsafe` не используется для идентификации.
2. Сервер выбирает секрет настроенного бота. Реализованный верификатор проверяет HMAC-SHA-256 по правилам Telegram, сравнивает хэши в постоянном времени и принимает `auth_date` возрастом до 5 минут. Допуск часов вперёд — 30 секунд. Он отклоняет дубликаты параметров, отсутствующую или неверную подпись, некорректный ID и просроченные запуски. Исходные данные запуска и токен бота исключаются из логов и URL. [Проверка данных запуска](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app)
3. Посредник привязывает запрос к короткоживущей транзакции браузера и намерению `login` или `link`. До выдачи кода он атомарно резервирует `replayKey` в общем хранилище с уникальностью по боту и TTL до `expiresAt`. Другая транзакция с тем же доказательством отклоняется. После сетевого сбоя продолжить транзакцию может тот же браузер. Недоступность хранилища прерывает обмен. Проверка времени сама по себе не обеспечивает однократность.
4. Посредник выдаёт Supabase короткоживущий одноразовый OIDC-код с фиксированным callback. Roomlet завершает PKCE-обмен через `exchangeCodeForSession`, сохраняет обычную SSR-сессию Supabase и открывает исходную внутреннюю страницу. Обновление, выход и отзыв доступа используют существующие механизмы. Если открыт другой аккаунт, переход к привязке требует явного выбора и свежего подтверждения.

## Web Store после подключения

В BotFather регистрируют HTTPS callback посредника, получают Client ID и Client Secret. Посредник проходит официальный Telegram Authorization Code Flow с PKCE S256. Одноразовые `state` и `nonce` связаны с браузером, целевой страницей и типом операции. Достаточно `openid profile`. Telegram возвращает профиль в ID-токене и не предоставляет отдельный UserInfo endpoint. Серверная OIDC-библиотека должна проверить подпись по доверенному Telegram JWKS, `iss=https://oauth.telegram.org`, ожидаемый `aud`, срок и исходный nonce. [Официальный Telegram Login](https://core.telegram.org/bots/telegram-login#openid-connect)

В Supabase регистрируют один custom OIDC provider, например `custom:roomlet-telegram`, с issuer посредника и его JWKS. Для входа без почты нужна опция `email_optional: true`. Посредник не выдаёт claim email. Секрет клиента Telegram, токен бота и отдельный секрет клиента Supabase у посредника имеют разные назначения. Roomlet использует `signInWithOAuth`; сессия появляется после штатной проверки провайдера и обмена кода. Приложение не выпускает собственный Supabase JWT. [Custom OIDC в Supabase](https://supabase.com/docs/guides/auth/custom-oauth-providers)

## Привязка и доступ

Вошедший пользователь явно выбирает привязку в настройках и подтверждает текущий аккаунт и Telegram. После включения manual linking Roomlet использует `linkIdentity` для того же провайдера. Callback сверяет исходный UUID и намерение, завершает обмен в этой сессии. Повтор для того же субъекта и UUID идемпотентен. Если субъект занят другим UUID, операция возвращает конфликт и сохраняет обе учётные записи. Сопоставление по отображаемому имени, username и введённым контактам исключено. Почтовый способ входа владельца и мастера остаётся доступен. [Identity linking в Supabase](https://supabase.com/docs/guides/auth/auth-identity-linking)

Триггер `profile_for_signup()` создаёт профиль с ролью `customer`, в том числе при пустом email. Studio проверяет `auth.getUser()` и читает роль из `profiles`. Влияния Telegram, user metadata и localStorage на права нет. Поэтому новая схема идентификации не требует миграции UUID, ролей или ослабления RLS. [Схема доступа Roomlet](SCHEMA.md)

Имя и язык Telegram могут отсутствовать. Почта обязательна только при email-регистрации. Телефон, адрес и предпочтительный способ связи относятся к оформлению заказа. Разрешение Telegram писать пользователю и добровольное согласие на маркетинг учитываются отдельно. Маркетинг выключен по умолчанию; настройки сервисных уведомлений независимы.

## Проверка в HTTPS-окружении до активации

Сначала на тестовом боте и отдельном проекте Supabase настроить точные адреса обоих callback, посредник, защиту от повторного обмена, секреты и custom provider. Убедиться, что вход одного Telegram-пользователя из двух каналов в любом порядке возвращает один UUID, включая одновременный первый вход. Проверить повтор после сетевого сбоя, отмену разрешения, устаревшее доказательство, смену username, попытку повторного обмена в другом браузере и конфликт занятого аккаунта. На существующем тестовом владельце проверить явную привязку и сохранение почтового входа, UUID и роли. Вход по Telegram включается после прохождения этих проверок.

Для локальной проверки верификатора и совместимости с PostgreSQL выполните из корня проекта `node --experimental-strip-types --experimental-test-isolation=none --test tests/telegram.test.ts tests/database.test.ts`. Тесты используют синтетические подписи и не обращаются к Telegram.
